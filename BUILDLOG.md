# BUILDLOG.md

Honest log of where AI (Claude) helped, where it was wrong, and what I changed.

## Where AI helped

- Schema design. I initially conflated `subject` and `category`, and wrote `attributes` as a paragraph instead of a list of discrete, visually-observable tags. Claude pushed back on both, pointing out that a sentence can't be compared programmatically the way a list can, and that I was reaching for facts (weight, pack-hunting behavior) that aren't actually visible in a still photo. I rewrote the attributes myself based on that feedback (fur color, ear size, tail tip color, snout shape).
- Data model design. I understood that images/tags/embeddings should be separate tables, but the reasoning (independent lifecycles: upload vs classify vs embed, each of which can fail/retry independently) was explained by Claude, and I confirmed I understood it before we wrote the SQL.
- Provider debugging. Vision API integration hit real infrastructure walls: OpenAI billing, Gemini free-tier quota (limit 0 on one model, 20/day on another), and Groq having no vision-capable model on my account at all. Claude helped me diagnose each one systematically (checking env variables, listing actually-available models via the API instead of guessing model names, isolating whether an issue was network vs quota vs account-level) rather than randomly retrying.
- Boilerplate code. Given time pressure partway through, I explicitly asked for full working files instead of writing every line myself (documented below as a deliberate scope tradeoff, not an oversight).

## Where AI was wrong, and what I did about it

- Model name guessing. Claude repeatedly suggested Gemini model names (gemini-2.5-flash, gemini-1.5-flash, gemini-2.0-flash) that turned out to be deprecated or unavailable on my account, each producing a 404 error. I pushed for a more reliable approach, listing my account's actually available models directly via the API, instead of continuing to guess.
- Overconfident claim about API key format. Claude asserted my real Gemini API key (prefixed AQ. instead of the more common AIzaSy...) "wasn't a valid key," based on outdated assumptions about Google's key formats. I tested it directly against the API anyway, it worked, and Claude corrected itself. Lesson: verify claims about external services empirically rather than trusting confident-sounding assertions, including from an AI assistant.
- First guard implementation missed a real edge case. The initial subject-match check used exact string equality between the image's subject and the inferred post subject, which would have incorrectly rejected a real image in my own corpus classified as "tibetan wolf" instead of "gray wolf". I caught this by actually running the guard against real data before finalizing it, and we changed the check to a substring match on the core species word instead.

## Deliberate tradeoffs I made

- Scope/pace tradeoff under time pressure. I started this project wanting to write every line myself. Partway through, after several unplanned hours lost to provider infrastructure issues (see above), I asked for larger, complete-file code drops instead of line-by-line guidance, to protect my submission deadline. I still reviewed, ran, and debugged every file myself (including fixing real bugs: a PowerShell redirection incompatibility, an indentation error, a Postgres port conflict between a native install and Docker), so I can explain what each file does, but I want to be transparent that the typing of some files was AI-generated rather than hand-written by me from scratch.
- Keyword-based subject inference instead of an LLM call. The guard's subject-inference step uses a fixed keyword dictionary rather than another AI call to interpret the post. This was a deliberate choice for determinism, auditability, and zero extra API cost, but it has a real, demonstrated limitation: a post like "this wolf-like dog was howling in my backyard" gets classified as being about a wolf because the word "wolf" appears, even though the post is arguably more about a dog. I found this by testing the guard against phrasing I hadn't originally planned for, and documented it honestly in the README rather than hiding it.
- Cost tracking added mid-project, not from the start. The api_calls logging table was added after the initial 49-image classification batch had already run, so that batch's real cost isn't captured, only the embedding step and one test classification call are logged. I chose not to re-run the full batch just to backfill logging, given free-tier quota constraints, and documented this gap explicitly in the README instead of hiding it.
